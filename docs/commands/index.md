# Skills (Slash Commands)

A guide to the SDD skills for Claude Code and Codex.

## Overview

When you run `sdd init`, 30 English SDD workflow skills are automatically created under `.claude/skills/sdd-*/SKILL.md`. Claude Code exposes each skill as a slash command, so you invoke them as `/sdd-start`, `/sdd-spec`, and so on (kebab-case).

- **30 sdd-* skills** in `.claude/skills/sdd-*/` — invoked as `/sdd-<name>` in Claude Code
- The same skills are generated for OpenAI Codex under `.agents/skills/sdd-*/` and invoked as `$sdd-<name>` (e.g. `$sdd-spec`) or picked from `/skills`. See [sdd init › Codex Support](/cli/init#codex-support).
- `.claude/commands/` is **not** generated by default. Claude Code merges custom commands into skills, so skills are the supported format.
- To additionally write the legacy Korean dot-notation commands (`.claude/commands/sdd.*.md`), run `sdd init --legacy-commands`.
- Use `--no-skills` to skip skill generation.
- Three subagents are generated with the skills (`.claude/agents/`, `.codex/agents/`): `sdd-spec-reviewer`, `sdd-implementer`, `sdd-impact-analyst`.
- Skill names below are the skill itself; lines starting with `sdd ...` are CLI commands you run in a terminal.

::: tip `<feature>` argument
Wherever a skill takes `<feature>` for an existing feature, pass `<domain>/<feature>` (e.g. `auth/login`) or the bare feature name when it is unique in the project (e.g. `login`). Only creating a new feature uses `<domain>/<feature>` (`/sdd-spec auth/login`).
:::

## Skill List

The **Mode** column shows how a skill runs (see [Skill Frontmatter](#skill-frontmatter)): **fork** = runs in a forked (isolated) context, **manual** = only you can invoke it, never the model on its own.

### Core Workflow

| Skill | Arguments | Description | Mode |
|-------|-----------|-------------|------|
| [`/sdd-start`](/commands/sdd-start) | — | Unified entry point: checks setup, then recommends the next skill | |
| [`/sdd-constitution`](/commands/sdd-constitution) | — | Create/edit the project constitution and bump its version | |
| [`/sdd-spec`](/commands/sdd-spec) | `<domain>/<feature>` | **Create/modify feature specs (unified)** | |
| [`/sdd-plan`](/commands/sdd-plan) | `<feature>` | Write `plan.md` | |
| [`/sdd-tasks`](/commands/sdd-tasks) | `<feature>` | Break the plan into `tasks.md` | |
| [`/sdd-prepare`](/commands/sdd-prepare) | `<feature> [--dry-run]` | Detect and generate needed subagents/skills | |
| [`/sdd-implement`](/commands/sdd-implement) | `<feature>` | Test-first, one task at a time | |
| [`/sdd-validate`](/commands/sdd-validate) | `[path] [--strict]` | Spec validation | |

> **Note**: `/sdd-spec` creates a new spec or modifies an existing one. Large modifications go through a change proposal under `.sdd/changes/CHG-xxx/{proposal,delta,tasks}.md`, which you apply with `sdd change apply <id>` and archive with `sdd change archive <id>`.

The core flow is `/sdd-spec` → `/sdd-plan` → `/sdd-tasks` → `/sdd-implement` → `/sdd-validate`. See [`/sdd-implement`](/commands/sdd-implement) for how task status and `sdd sync` fit in.

### Skill Frontmatter

Each Claude Code skill's `SKILL.md` uses these frontmatter fields:

| Field | Applied to |
|-------|-----------|
| `context: fork` | 6 analysis skills (`sdd-analyze`, `sdd-impact`, `sdd-report`, `sdd-research`, `sdd-search`, `sdd-sync`) — run in an isolated context |
| `disable-model-invocation: true` | 5 utility skills (`sdd-chat`, `sdd-cicd`, `sdd-guide`, `sdd-migrate`, `sdd-watch`) — only you can invoke them |
| `argument-hint` | Skills that take arguments |
| `allowed-tools` | All sdd-* skills — least-privilege patterns (e.g., `Bash(sdd validate*)`) |

Codex skills (`.agents/skills/`) carry only `name` and `description`. The five manual-only skills get an `agents/openai.yaml` with `policy.allow_implicit_invocation: false` instead.

## Usage

Enter skills starting with a slash in Claude Code (or `$` in Codex):

```
/sdd-start
```

When arguments are needed:

```
/sdd-spec auth/login
/sdd-implement auth/login
```

In Codex the same calls are `$sdd-spec auth/login` and `$sdd-implement auth/login`.

## Examples

### Reverse Engineering Workflow

Extract SDD specs from legacy code. The AI reads the code and writes drafts; the CLI scans, validates, reviews, and finalizes:

Run `/sdd-reverse`; it guides you through scanning the project, drafting specs from the code, reviewing the drafts, and finalizing them. See [/sdd-reverse](/commands/sdd-reverse) for details.

```
/sdd-reverse                              # AI-driven: scan, read code, write drafts
sdd validate .sdd/.reverse-drafts         # Validate drafts
sdd reverse review --list                 # Review drafts
sdd reverse review <ref> --approve        # Approve (after confirmation)
sdd reverse finalize                      # Move approved drafts to .sdd/specs/
```

### Domain System

Logically group large projects:

```
/sdd-domain create auth        # Create domain
/sdd-domain graph              # Dependency graph
/sdd-context set auth payment  # Set working context
```
